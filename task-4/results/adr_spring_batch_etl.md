## Нефункциональные требования

Опишите здесь нефункциональные требования и архитектурно значимые требования.

| **№** | **Требование**                                                                                                                                     |
|:-----:|:---------------------------------------------------------------------------------------------------------------------------------------------------|
|   1   | **Производительность**: Среднее время обработки файла на 2 000 строк не должно превышать 30 секунд                                                 |
|   2   | **Масштабируемость**: Система должна поддерживать 100-150 параллельных загрузок в пиковые часы                                                     |
|   3   | **Надежность**: Система должна автоматически восстанавливаться после сбоев с использованием механизмов retry и restart                             |
|   4   | **Пиковая нагрузка**: Обработка до 1 200 000 строк в сутки (в 2-3 раза выше базовой нагрузки в 400 000 строк)                                      |
|   5   | **Отказоустойчивость**: При падении задания должна быть возможность перезапуска с точки остановки без повторной обработки уже обработанных записей |
|   6   | **Интеграция**: Решение должно интегрироваться с существующей Java/WildFly экосистемой                                                             |
|   7   | **Расширяемость**: Архитектура должна позволять добавление новых этапов обработки и источников данных без значительной переработки                 |
|   8   | **Мониторинг**: Система должна предоставлять метрики выполнения заданий, количество обработанных записей, ошибки                                   |
|   9   | **Размер чанка**: Оптимальный размер пакета для batch-обработки должен балансировать между производительностью и стабильностью                     |
|  10   | **Транзакционность**: Обработка должна быть транзакционной на уровне чанков для обеспечения целостности данных                                     |

## Решение

### Архитектурное решение: Spring Batch

Для решения задачи пакетной обработки данных предлагается внедрение **Spring Batch** — зрелого фреймворка для
batch-обработки в Java-экосистеме.

### Архитектура решения

#### Основные компоненты Spring Batch:

1. **Job** — определение batch-задания для обработки файла отчета
2. **Step** — шаги обработки:
    - Валидация файла
    - Чтение и парсинг CSV
    - Обогащение данными из справочников
    - Запись в БД номенклатуры
3. **ItemReader** — компонент для чтения данных из CSV-файла в GCS
4. **ItemProcessor** — компонент для валидации и обогащения данных
5. **ItemWriter** — компонент для batch-записи в PostgreSQL
6. **JobRepository** — хранилище метаданных о выполнении заданий (PostgreSQL)
7. **JobLauncher** — запуск заданий через REST API из WildFly приложения

#### Поток обработки данных:

```
Пользователь → Web UI (Angular)
    → Backend API (WildFly)
    → Сохранение файла в GCS
    → Запуск Spring Batch Job
    → ItemReader (чтение из GCS)
    → ItemProcessor (валидация + обогащение из БД справочников)
    → ItemWriter (batch-insert в БД номенклатуры)
    → Уведомление пользователя о результате
```

#### Технические детали:

**1. Chunk-ориентированная обработка:**

- Данные обрабатываются порциями (chunks) по 500-1000 записей
- Каждый chunk обрабатывается в отдельной транзакции
- При ошибке откатывается только текущий chunk, а не вся обработка

**2. Параллелизация:**

- **Multi-threaded Step**: обработка одного файла в несколько потоков
- **Parallel Steps**: одновременное выполнение независимых шагов
- **Partitioning**: разделение большого файла на части для параллельной обработки
- **Remote Chunking**: распределение обработки между несколькими инстансами

**3. Отказоустойчивость:**

- **Skip Policy**: пропуск невалидных записей с логированием ошибок
- **Retry Policy**: автоматический retry при транзиентных ошибках (3 попытки с экспоненциальной задержкой)
- **Restart**: возможность перезапуска упавшего задания с точки остановки

**4. Интеграция с существующей инфраструктурой:**

- Spring Batch приложение развертывается как отдельный микросервис
- Взаимодействие с WildFly через REST API для запуска заданий
- Использование существующих PostgreSQL БД
- Чтение файлов из Google Cloud Storage через Google Cloud Storage client library

**5. Оптимизация размера чанка:**

Для файла на 2000 строк с требованием обработки за 30 секунд:

- **Chunk size: 500 записей** — оптимальный баланс между:
    - Производительностью (меньше транзакций, больше batch-insert)
    - Стабильностью (при ошибке откат меньшего объема данных)
    - Потреблением памяти (контроль heap size)

Диаграмма демонстрирует:

- **Context level**: взаимодействие пользователей, систем и Spring Batch компонента
- **Container level**: детализация компонентов (Frontend, Backend, Spring Batch Service, БД, GCS)
- **Component level**: внутренняя структура Spring Batch (Job, Steps, Reader/Processor/Writer)

### Логика принятия решения

**Почему Spring Batch:**

1. **Интеграция с Java-экосистемой**: Бесшовная интеграция с существующим WildFly/Java 11 стеком
2. **Зрелость и надежность**: Проверенное enterprise-решение с 15+ летней историей
3. **Rich функциональность**: Встроенные механизмы retry, skip, restart, partitioning
4. **Chunk-based processing**: Эффективная обработка больших объемов данных с контролем транзакций
5. **Мониторинг**: Встроенная поддержка метрик и интеграция с Spring Boot Actuator, Micrometer
6. **Масштабируемость**: Поддержка параллелизма и распределенной обработки
7. **Community и поддержка**: Большое community, обширная документация, Spring экосистема
8. **Миграция к микросервисам**: Spring Batch service легко выносится в отдельный микросервис

**Покрытие функциональных требований:**

- ✅ Чтение CSV из GCS — FlatFileItemReader с GCS client
- ✅ Валидация данных — ValidatingItemProcessor
- ✅ Обогащение справочными данными — Custom ItemProcessor с JDBC запросами
- ✅ Batch-запись в БД — JdbcBatchItemWriter
- ✅ Параллельная обработка — Multi-threading + Partitioning
- ✅ Retry и error handling — @RetryTemplate, Skip/Retry Policies
- ✅ Уведомления — JobExecutionListener для callback

**Покрытие нефункциональных требований:**

- ✅ Производительность 30 сек/2000 строк — chunk size 500, multi-threading
- ✅ 100-150 параллельных загрузок — горизонтальное масштабирование Spring Batch instances
- ✅ Обработка 1.2М строк/сутки — partitioning + параллельные джобы
- ✅ Отказоустойчивость — restart capability, JobRepository
- ✅ Мониторинг — Spring Boot Actuator + Micrometer → Prometheus

## Альтернативы

### 1. Apache Airflow

**Описание:** Платформа для оркестрации workflow и ETL-пайплайнов на Python.

**Преимущества:**

- Визуальный UI для мониторинга DAG (Directed Acyclic Graphs)
- Богатая экосистема операторов для интеграции с различными системами
- Гибкость Python для сложной логики
- Distributed scheduling

**Недостатки:**

- Необходимость внедрения Python-стека в Java-ориентированную инфраструктуру
- Дополнительная сложность интеграции (Java ↔ Python)
- Overhead для относительно простых batch-операций
- Требует дополнительную инфраструктуру (Airflow webserver, scheduler, executor)

**Вердикт:** Избыточно для текущих требований, усложняет tech stack.

---

### 2. AWS Glue / Google Cloud Dataflow

**Описание:** Managed ETL-сервисы от облачных провайдеров.

**Преимущества:**

- Полностью управляемые сервисы (serverless)
- Автоматическое масштабирование
- Интеграция с облачными хранилищами и БД
- Встроенный мониторинг

**Недостатки:**

- Vendor lock-in на конкретного провайдера
- Ограниченная кастомизация логики обработки
- Стоимость при высоких объемах
- Меньший контроль над инфраструктурой
- Сложность локальной разработки и тестирования

**Вердикт:** Хорошо для долгосрочной перспективы, но требует миграции архитектуры.

---

### 3. Custom Python ETL (Pandas + multiprocessing)

**Описание:** Разработка собственного ETL-решения на Python с использованием Pandas для обработки данных.

**Преимущества:**

- Полный контроль над логикой
- Pandas эффективен для data manipulation
- Простота разработки для простых сценариев
- Легковесность

**Недостатки:**

- Необходимость самостоятельной реализации retry, restart, мониторинга
- Сложность поддержки транзакционности
- Интеграция с Java-бэкендом требует дополнительной работы
- Нет встроенных enterprise-паттернов batch-обработки
- Требуется время на разработку и тестирование

**Вердикт:** Подходит для прототипирования, но недостаточно зрелое решение для production.

---

### 4. Apache NiFi

**Описание:** Система для автоматизации потоков данных с визуальным UI.

**Преимущества:**

- Визуальное проектирование data flows
- Встроенные процессоры для различных источников/назначений
- Backpressure и prioritization
- Data provenance

**Недостатки:**

- Избыточен для batch-обработки файлов
- Больше ориентирован на real-time streaming
- Дополнительная инфраструктура
- Более высокая сложность для простых ETL-задач

**Вердикт:** Избыточно для текущих требований.

---

### 5. Quartz Scheduler + Custom Java Code

**Описание:** Использование Quartz для scheduling и собственный код для обработки.

**Преимущества:**

- Lightweight решение
- Полный контроль над логикой
- Интеграция с существующим Java-кодом

**Недостатки:**

- Необходимость реализации всех batch-паттернов с нуля
- Нет встроенной поддержки chunk processing, retry, restart
- Сложность масштабирования
- Больше времени на разработку

**Вердикт:** Слишком низкоуровневое решение, требует значительных усилий на разработку.

## Недостатки, ограничения, риски

### Недостатки Spring Batch:

1. **Сложность конфигурации**: Spring Batch имеет steep learning curve, требуется время на изучение концепций (Job,
   Step, Chunk)
2. **Overhead для простых задач**: Для очень простых ETL-операций может показаться избыточным
3. **XML/Java конфигурация**: Хотя есть Java-based config, многие примеры используют XML
4. **Debugging сложность**: Отладка batch-заданий может быть сложнее по сравнению с синхронным кодом

### Ограничения:

1. **JVM-привязка**: Решение работает только в JVM-экосистеме
2. **Ресурсоемкость**: Spring Boot приложение с Spring Batch требует достаточно памяти (рекомендуется минимум 1GB heap)
3. **Latency**: Batch-обработка не подходит для real-time требований (есть минимальная задержка на запуск джоба)
4. **JobRepository overhead**: Метаданные batch-заданий хранятся в БД, что создает дополнительную нагрузку

### Риски:

1. **Риск неправильного выбора chunk size**:
    - *Митигация*: Нагрузочное тестирование для определения оптимального размера

2. **Риск deadlock при параллельной обработке**:
    - *Митигация*: Правильная настройка уровней изоляции транзакций, connection pooling

3. **Риск переполнения heap при больших файлах**:
    - *Митигация*: Streaming читателей, chunk processing, мониторинг памяти

4. **Риск узкого места в БД при пиковых нагрузках**:
    - *Митигация*: Connection pooling, read replicas для справочников, batch-insert оптимизация

5. **Сложность миграции существующего кода**:
    - *Митигация*: Поэтапная миграция, начиная с новых функций, постепенный перенос legacy кода

6. **Операционная сложность при масштабировании**:
    - *Митигация*: Использование Kubernetes для оркестрации, автоскейлинг на основе метрик очереди

7. **Недостаток опыта команды в Spring Batch**:
    - *Митигация*: Обучение команды, привлечение консультантов на начальном этапе, создание внутренней документации

**Фаза 1** (2-3 недели): Proof of Concept

- Разработка минимального Spring Batch джоба для обработки CSV
- Тестирование на реальных данных
- Валидация производительности

**Фаза 2** (1 месяц): MVP

- Полная реализация ETL пайплайна
- Интеграция с WildFly backend
- Базовый мониторинг

**Фаза 3** (1-2 месяца): Production Ready

- Horizontal scaling
- Advanced retry policies
- Comprehensive мониторинг и алертинг
- Документация и training

**Фаза 4** (ongoing): Оптимизация

- Тюнинг производительности на основе реальной нагрузки
- Расширение функциональности
- Миграция legacy batch-операций
